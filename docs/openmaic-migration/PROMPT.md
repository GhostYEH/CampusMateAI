# 启动提示词（完成剩余全部工作）

> **使用方式**：把下面「提示词正文」整段复制给 Codex。
> 复制前，把正文第一行的 `【参考项目根目录】` 替换成参考项目（OpenMAIC v1.0.x 源码）的
> 实际绝对路径。
> 用占位符而非真实路径，是因为仓库规则（`AGENTS.md`）禁止把本机路径写进提交物。

## 提示词正文

```text
参考项目根目录 = 【参考项目根目录】

你是本仓库的长期执行者。目标：把 docs/openmaic-migration/03-待办.md 里
「优先级 1 ～ 优先级 5」的剩余工作**全部做完**，直到那份清单里再没有可做的项。

不要中途停下来问我"要不要继续"。除非遇到下面第 7 节定义的"必须停下来问"的情况，
否则一路做完，最后给我一份总报告。

================================================================
1. 先读文档（按顺序，别跳）
================================================================

1) docs/openmaic-migration/README.md      —— 索引与全局
2) docs/openmaic-migration/01-约束.md      —— 架构边界与红线（违反等于白做）
3) docs/openmaic-migration/04-陷阱.md      —— 12 条已踩过的坑（能省你几小时）
4) docs/openmaic-migration/03-待办.md      —— 你要做的事，按优先级
5) docs/openmaic-migration/02-现状.md      —— 已完成什么、代码在哪（别重做、别弄坏）
6) docs/openmaic-migration/05-工程规范.md  —— 测试 / 验收 / 提交 / 交付口径
7) docs/openmaic-migration/06-参考实现地图.md —— 参考项目哪个文件对应哪块
8) AGENTS.md                              —— 仓库级规则，优先于以上所有习惯性建议

读完先跑一次基线，确认现状与你读到的一致：

  前端：  cd webreact         && npm test          （期望全绿）
  服务：  cd openmaic-service && npm test && npm run typecheck
  后端：  cd backend          && .\.venv\Scripts\python.exe -m pytest tests -k openmaic -q

如果基线不是绿的，**先停下来告诉我**——说明有人改坏了东西，不要在坏基线上叠加改动。

================================================================
2. 工作方式：切片推进 + 进度账本
================================================================

- 把 03-待办.md 的每一项拆成**可独立验收的切片**，一次只做一个切片。
- **每个切片必须完整走完第 3 节的"完成定义"**（代码 + 测试 + 真实浏览器验收 +
  能力矩阵 + 提交），不许攒着一起做。
- 每个切片结束后，**立刻更新进度账本** `docs/openmaic-migration/PROGRESS.md`：
  已完成哪些切片、各自提交号、下一个要做什么、有没有卡住的项。
  这个账本是你跨上下文存活的唯一凭据——你的上下文随时可能被截断或被重开，
  断掉之后**从账本继续，不要从零重来**。
- 一旦发现上下文开始吃紧（感觉前面的细节记不清了），
  主动把当前进度写进账本，然后重读账本 + 03-待办.md 再继续。

================================================================
3. 一个切片的"完成定义"（缺一条都不算完成）
================================================================

1) 代码写完，且**逐字对齐参考实现**：类名、内联样式、DOM 结构保持与上游一致，
   只做机械改写（擦 TypeScript 类型、换 import 路径、去 'use client'、
   next/* 换成普通标签、t() 换成简体中文）。
   每一处**有意不同**都要在代码注释里写明原因。
2) 补测试。照仓库现有风格：
   - 前端 `webreact/tests/*.test.mjs`（node --test），大量使用源码级契约断言；
   - 服务端 `openmaic-service/tests/*.test.mjs`（node --experimental-strip-types --test），
     优先测纯函数。
   注意：**源码级断言挡不住逻辑错误**（见 04-陷阱.md 第 6 条），关键链路必须真跑。
3) **真实浏览器验收（Playwright，不许 mock 后端）**，并给出**具体数字**：
   - 几何 / 文本的实测值（例如"面板高 192px、三列 [90, 1135, 140]"）；
   - pageerror 条数、console error 条数、>=400 的 API 响应条数（写"0 条"而不是"没发现问题"）；
   - 窄屏至少验 320px；
   - 截图留证（截图不入库，用完删）。
4) 跑一遍质量门并全绿（命令见 05-工程规范.md）。
5) 更新 `docs/openmaic-capability-matrix.md`：新增/改变的能力要有对应行，
   且**没有浏览器证据不许写"已验证"**。
6) **一次提交**，提交信息聚焦 why、用中文。
   只暂存本次切片相关文件；工作区里有别人未提交的改动（见第 4 节），不要一起提交。

================================================================
4. 并发警告（很重要）
================================================================

**这个仓库可能同时有别的会话在改代码。** 起草本提示词时，另一个会话正在开发
「场景讲解音频」功能，涉及 `openmaic-service`（tts / jobs / db / provider / main）
以及 `webreact`（`components/openmaic/**`、`data/api.js`、`features/openmaic/**`）。

**不要依赖上面这份清单**——它会过期。用下面的规则自己判断：

1. **开工第一件事：跑 `git status`。** 凡是"已修改但未提交"或"未跟踪"的文件，
   只要**不是你这次会话创建的**，一律当作别人的工作。
2. **默认不碰别人的文件**，也不提交它们（**禁止 `git add -A` / `git add .`**，
   永远只 `git add <你明确改过的路径>`）。
3. 你不可避免会用到别人正在改的文件（例如 `OpenMAICClassroomStage.jsx`
   既是集成层、又可能是别人正在扩展的地方）。**动这类文件前，先 `git diff` 看一遍
   别人已经改了什么**，在你的改动里保留他们的部分，不要覆盖。
4. 若你判断必须**重写**别人正在改的文件，或者必须改 `openmaic-service` 的
   tts / jobs / db / provider —— **停下来问我**（见第 7 节）。
5. 提交前再跑一次 `git status`，确认暂存区里只有你自己的文件。

================================================================
5. 不许做的事
================================================================

- 不许违反 01-约束.md 的红线：浏览器只调 CampusMate API、不直连 :4010、
  不引入第二套登录/导航/课程库、不把产品外壳放进 iframe、
  不引入 Tailwind preflight、令牌不外溢到 .maic-root 之外。
- 不许把参考项目的路径写进任何提交物；不许把它的二进制资源拷进仓库
  （那要走 third_party/ 的 LICENSE / NOTICE / SHA 清单流程）。
- 不许提交：截图、日志、临时脚本、构建产物、.env、本机绝对路径。
- **不许假装有能力**：没有对应运行时的功能（PBL workspace 阶段、
  圆桌的实时流式 / 逐智能体 TTS / ASR / 真人头像图）
  **不要渲染入口，也不要放点了没反应的死按钮**。
- 不许为了让测试变绿而放宽断言、跳过用例、或改测试去迁就实现。
  断言确实过时了（因为契约有意变了）可以改，但必须说明为什么。

================================================================
6. 遇到"做不了"怎么办
================================================================

03-待办.md 的最后两节已经写明哪些是**架构上做不了**的（缺运行时）。
除此之外你可能会发现新的做不了的项。处理方式：

1. 在 `PROGRESS.md` 里记一行：`[无法完成] <项> —— <具体原因>`；
2. 在 03-待办.md 对应项下面补一句同样的话；
3. **保持显式占位、不要伪造**；
4. **继续做剩下的项**，不要因为一项做不了就停住整轮。

================================================================
7. 必须停下来问我的情况（只有这三种）
================================================================

1. 基线测试不是绿的（说明有人改坏了东西）。
2. 你判断某个改动会**破坏已有契约**（例如必须改公开 API、改数据库结构、
   或让既有测试失效且不是"断言过时"而是真的行为倒退）。
3. 你发现必须先改 `openmaic-service` 的 tts / jobs / provider / migrations
   （那是另一个会话的地盘）。

其它情况一律自己决定并继续。

================================================================
8. 最终交付：给我一份总报告
================================================================

全部做完（或做到 03-待办.md 里再没有可做的项）之后，报告：

1. **逐条对照 03-待办.md**，说明每项：已做完 / 做不了（附原因）。
2. 每个切片的：提交号、改了哪些文件、对齐了参考项目的哪个文件哪一段。
3. 与参考**有意不同**的地方，以及为什么（"没有对应运行时"是正当理由，
   "顺手简化了"不是）。
4. 最终质量门结果：三个测试套件的通过数、构建结果、
   真实浏览器验收里关键几何/文本的实测值、pageerror 与 console error 的条数。
5. 你**没能做完**的项，以及它们各自卡在哪。
6. 你过程中发现的、这份文档没提到的坑（我会补进 04-陷阱.md）。

报告写完之前不要停止。现在开始：先读文档、跑基线，然后告诉我你读完的理解
和你的切片计划，接着直接开始做第一个切片。
```
