# Web 学习通连接与多端同步设计

## 目标

在不修改 Android 与鸿蒙代码的前提下，为学生 Web 端补齐学习通账号连接、状态检查、手动同步、重新登录和解除连接能力。同步所得课程、作业与通知必须写入后端 SQLite，并以 CampusMate 当前 JWT 账号为隔离边界，使同一账号在 Web、Android 和鸿蒙端读取同一份后端数据。

本次不实现浏览器读取微信、QQ 或其他应用的系统通知。该能力依赖移动操作系统通知权限，不属于 Web 学习通连接范围。

## 已有实现与约束

- Android 已有完整学习通连接流程：检查状态、账号登录、同步、状态统计、失效重登、解除连接及周期同步。
- Web 已有学习通 API 封装和两张页面，但挂在孤立的 `/teacher/chaoxing` 路由下，与项目仅有学生和管理员两种角色的约束冲突，学生端也没有正式入口。
- 后端已有 `/chaoxing/login`、`/chaoxing/status`、`/chaoxing/sync` 和 `/chaoxing/disconnect`，并使用当前 JWT 用户 ID 存取学习通凭证。
- 学习通 Cookie 经后端加密后保存在 `chaoxing_credentials`；学习通密码只用于远端登录，不在浏览器或数据库中持久化。
- 课程、个人待办和学习通通知已分别落入 `courses`、`personal_tasks` 与 `notices` 表，并以当前 CampusMate 用户 ID 隔离。
- 工作区存在用户未提交改动。实现必须增量保留这些改动，且不得编辑 `android/` 或 `harmony/` 下任何文件。

## 方案选择

采用独立学生页面方案：

1. 学习通连接页使用学生路由 `/profile/chaoxing`。
2. “通知整理”页与“个人中心”各提供入口。
3. 旧 `/teacher/chaoxing` 和 `/teacher/chaoxing/login` 保留兼容重定向，避免旧链接立即失效。
4. 复用现有后端学习通端点，不引入第二套协议或数据模型。

未采用直接嵌入通知页的方案，因为登录、状态、同步统计和异常恢复会使通知页职责过重。未采用继续暴露教师路由的方案，因为项目不存在教师角色，继续使用该命名会固化错误边界。

## Web 信息架构与交互

### 路由与入口

- 新增学生路由 `/profile/chaoxing`，由学生 `AppShell` 承载。
- “通知整理”页头提供“连接学习通”或“管理学习通”入口，文案根据连接状态变化不是必需条件；入口本身始终可用。
- 个人中心“我的工具”增加“学习通同步”快捷入口。
- 旧教师学习通路由重定向至 `/profile/chaoxing`。

### 页面状态

页面使用一个连续流程，不再要求用户在状态页和独立登录页之间跳转：

- `checking`：首次进入或手动刷新时显示连接检查状态。
- `offline`：显示账号与密码输入框以及“登录并连接”。
- `online`：显示上次同步时间、数据来源、课程数、教师数、未完成作业数、通知数，并提供“立即同步”和“解除连接”。
- `expired`：显示失效提示、重新登录表单和“解除连接”。
- `unavailable`：保留当前连接信息，提示暂时无法验证，允许用户重试，不把网络失败当作解绑。

登录成功后清空内存中的密码。同步成功后重新拉取状态统计。同步或状态检查失败时保留用户当前可用状态，并显示可操作的错误提示。

页面视觉必须沿用学生 Web 现有设计语言、按钮、图标、色彩、圆角、响应式断点与加载反馈，不新增独立设计系统或图片资产。

## 后端数据流

1. Web 使用现有 Axios 客户端携带 CampusMate JWT。
2. `POST /chaoxing/login` 使用提交的学习通用户名和密码建立远端会话，仅保存加密 Cookie，键为当前 `user.id`。
3. `POST /chaoxing/sync` 读取该用户 Cookie，从学习通获取课程、作业和课程通知。
4. 数据按当前用户幂等写入：
   - 学习通课程：`courses.provider = 'chaoxing'`，所有者为当前用户；同一用户与远端课程 ID 唯一识别。
   - 学习通作业：`personal_tasks.user_id = 当前用户` 且 `source = 'chaoxing'`；同一用户、来源和远端 ID 幂等更新。
   - 学习通通知：`notices.user_id = 当前用户` 且 `source = 'chaoxing'`；同一用户、来源和远端 ID 幂等更新。
   - 可执行通知生成的待办仍以当前用户隔离，并复用现有去重策略。
5. `GET /chaoxing/status` 返回该用户的连接状态与数据库统计。
6. `POST /chaoxing/disconnect` 只删除该用户的学习通凭证；已同步课程、作业和通知保留，避免解除连接造成历史数据丢失。

以上数据均由各端使用同一 CampusMate JWT 账号读取，因此多端同步发生在后端数据库层，而不是依赖浏览器或手机本地缓存。

## Web 数据展示衔接

- 课程页继续调用 `GET /courses`。学生课程查询必须包含当前用户拥有的学习通导入课程。
- 待办页继续调用 `GET /tasks`，自动显示当前用户的学习通作业与从通知提取出的待办。
- 通知整理页在现有校内班级公告之外，增加 `GET /notices` 返回的用户学习通通知，并统一排序、搜索和来源筛选。
- 学习通通知没有校内公告的已读回执协议，因此只使用其自身可用字段，不调用校内公告的 `markAnnouncementRead` 接口。

## 异常与安全处理

- 学习通要求验证码时显示 `verification_required` 引导，提示先在官方 App 或网页完成验证。
- Cookie 失效返回 `expired`/重新登录语义，不删除已同步数据。
- 学习通或网络不可用返回 `unavailable`，不把连接状态错误地改成未连接。
- 密码输入使用浏览器密码字段，成功或失败后不写入 localStorage、Pinia 或数据库。
- 后端所有查询与写入必须带当前 JWT 用户 ID，测试须覆盖两个用户使用相同远端 ID 时互不覆盖。
- 同步重复执行不得生成重复课程、作业、通知或派生待办。

## 测试与验收

### 后端自动化测试

- 登录凭证按 JWT 用户写入且加密保存。
- 状态统计只计算当前用户的学习通数据。
- 两个用户使用相同学习通远端 ID 时课程、作业和通知相互隔离。
- 重复同步保持幂等。
- 解除连接只删除当前用户凭证，且保留其历史同步数据。
- 无凭证、会话失效、验证码和服务不可用返回稳定状态或错误码。
- 学习通课程可由对应学生账号通过 `/courses` 读取。
- 学习通通知可由对应学生账号通过 `/notices` 读取。

### Web 自动化测试

- `/profile/chaoxing` 注册为学生页面。
- 旧教师学习通 URL 重定向到新学生路由。
- 通知整理和个人中心均存在学习通入口。
- 学习通连接页调用既有四个后端接口，并覆盖状态、登录、同步和解除连接交互。
- 通知整理页同时请求校内公告与用户通知数据，并避免对学习通通知调用校内公告已读接口。
- `npm run build` 成功。

### 只读跨端审计

交付时附带 Android 与鸿蒙流程对照：

- Android：已具备学习通账号绑定、状态验证、手动同步、周期同步、失效恢复和解除连接。
- 鸿蒙：已具备微信、QQ、学习通等系统通知监听与通知转待办流程，但当前没有发现学习通账号登录、连接状态、后端拉取同步或解除连接页面。
- 因此两端在“系统通知监听”能力上方向一致，但在“学习通账号连接与后端同步”流程上不一致。该差异只报告，不修改鸿蒙代码。

## 完成标准

- 学生能从 Web 通知整理页或个人中心进入学习通同步页并完成全流程操作。
- 同一 CampusMate 账号在 Web 完成同步后，Android 与鸿蒙通过现有后端课程、任务和通知接口读取到同一份数据；不依赖 Web 本地存储。
- 不同 CampusMate 账号间学习通凭证与同步数据完全隔离。
- Android 与鸿蒙工作区文件在本次实现中零修改。
- 相关后端测试、Web 回归测试与 Web 构建全部通过。
