# HarmonyOS 全量动效系统设计

## 目标

在不改变业务接口、页面信息架构和现有视觉配色的前提下，为 HarmonyOS 客户端建立一致、克制且有活力的动效语言，覆盖登录、五个主 Tab、全部二级页面、公共导航组件以及加载和状态切换。

## 体验原则

- 风格采用“平衡灵动”：反馈明确，但不使用长时间、长距离或循环装饰动画。
- 动画帮助用户理解层级、状态和操作结果，不单纯追求视觉热闹。
- 首屏内容按区域错峰，最多四组；数据列表整体进入，不对长列表无限逐项延迟。
- 页面转场不阻塞点击，不改变网络请求、表单提交或路由状态。
- 深色模式与浅色模式共享同一套动效参数。
- “减少动态效果”是全局硬约束：关闭位移、缩放、错峰和持续动画，只允许即时更新或不超过 80ms 的淡入。

## 方案选择

采用公共动效基座。新增纯 ArkTS `MotionSpec`，集中提供快速反馈、状态变化、页面转场、错峰延迟、位移距离和按压缩放等数值，并根据 `reduceMotion` 返回安全降级值。页面和公共组件只消费这些值，不各自发明时长。

不采用页面独立参数，因为这会继续造成节奏分裂；不重构为新的导航框架，因为当前 `Index.ets` 正承载未提交的社区功能改动，导航重写会扩大回归面。

## 动效层级

### 页面与导航

- 主 Tab 继续使用 ArkUI `Tabs`，标准切换时长为 260ms；减少动态时为 0ms。
- 二级页面由当前全屏纵向升起改为 24vp 侧向位移加淡入，标准时长为 300ms。
- 登录成功、退出确认框和页面内详情切换使用淡入加轻微缩放，避免突然出现。

### 首屏内容

- 页面标题、英雄卡片、筛选/快捷操作和主体内容分为最多四个阶段。
- 每阶段间隔 35ms，整体在约 350ms 内稳定。
- 页面首次出现时执行一次；网络刷新不重复播放整页入场，只对加载态和内容态做短淡入。

### 操作反馈

- 小图标和圆形按钮按压至 0.90–0.92，卡片和大按钮按压至 0.96–0.97。
- 松手或定时恢复使用 140–160ms 快速曲线。
- Tab、筛选项、完成状态、进度值和展开区域使用 200–240ms 状态过渡。
- 循环动画仅保留系统 `LoadingProgress`；不新增常驻漂浮、呼吸或闪烁。

## 覆盖范围

- 公共层：`Index.ets`、`AppDock.ets`、`SecondaryHeader.ets`。
- 主流程：登录、首页、课程、待办、AI 校园助手、个人中心。
- 二级流程：考试、空教室、校园社区、大学/教务、专注、失物招领、通知、文件/活动/收藏、设置、账号、关于以及服务页。
- 所有页面接收同一个 `reduceMotion` 值；现有动画改为使用统一参数。

## 实现边界

- 不新增第三方依赖。
- 不修改后端、Android、Web 或微信小程序代码。
- 不改变 API 请求、数据模型、权限和业务状态机。
- 对当前未提交的 Harmony 社区改动只做必要的动效属性和参数传递，不重写其业务实现。

## 验证

- 为 `MotionSpec` 编写 Hypium 单元测试，验证标准模式和减少动态模式的可观察策略。
- 使用项目固定的 DevEco Studio / Harmony SDK 环境运行 Harmony 单元测试。
- 运行完整 `assembleApp --no-daemon`，以 ArkTS 编译器覆盖所有页面参数和动画 API。
- 检查最终 Git diff，确认没有覆盖现有未提交业务改动，也没有生成文件或其他平台改动混入。
